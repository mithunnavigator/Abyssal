# Site Onboarding and Continuous Backfill Specification

This specification describes how to onboard data leak sources with paginated lists into the unified `SiteAdapter` architecture. The goal is to discover new intelligence promptly while recoverably backfilling historical details. New sites reuse the pagination scheduler, pending-fetch queue and task execution entry point, and only implement the site-specific differences in requests, parsing and storage.

## Default budgets and statistics definitions

| Setting | Default | Purpose |
| --- | ---: | --- |
| `recent_pages_per_run` | 1 | Number of newest pages checked first per section per round |
| `backfill_pages_per_run` | 5 | Historical page budget for the whole site per round, distributed fairly across sections |
| `frontier_max_pending` | 500 | Backlog threshold for unfinished details, including tasks already claimed |
| `max_detail_pages_per_run` | Uses the site configuration | Claim quota for each replenishing dispatch |
| `max_concurrent_details` | Uses the site configuration | Maximum number of details executing at the same time for one site |

Historical cursors are saved per site and section and resume from the saved page number after a process restart; completed cursors are not rescanned from page two in the next round. Newest pages are checked continuously; when newest content needing processing is found, historical discovery pauses, otherwise the historical page budget is limited by the remaining dispatch window and the number of unfinished candidates. The threshold is the water mark at which historical discovery pauses; newest pages or bulk discovery on a single page can push database pending candidates above the mark, and candidates must still be saved in full.

The per-site dispatch window is fixed at `2 * max_concurrent_details`, and the window and candidate claims are checked in the same database transaction. Newest candidates take priority and historical tasks use a lower broker priority; free slots are refilled after details complete, without waiting for the next list scan.

`pending` are tasks that are not yet complete and not validly claimed, including tasks waiting for retry; `inflight` includes dispatch reservations, queued tasks and running tasks; `completed` are the tasks currently completed in the queue. They do not represent the source's total count, nor the number of new deduplicated intelligence records. Reaching the last page only means list discovery has finished scanning; details still need to be ingested successfully one by one.

## Adapter onboarding

1. Implement list and detail parsing in `sites/<site>.py`, providing a stable topic identifier, title, source URL, section and body-related version information.
2. Implement the existing `SiteAdapter` interface in `adapters/<site>.py` and declare use of the persistent pending-fetch mechanism with `supports_frontier = True`. MyBB forums reuse [collect_forum_seed](./src/darkweb_collector/adapters/pagination.py), and other paginated APIs reuse `collect_paginated_seed` from the same file, keeping pagination metadata; do not copy a separate queue scheduler into the adapter.
3. `plan_details` Return detail candidates that have been discovered and fall within the collection scope, without truncating them early by detail quota. The execution entry point persists the candidates, claims them fairly by section and then consumes this round's quota.
4. Register it in `adapters/registry.py` and set the actual entry points, pagination budget, detail budget and fetch method in `sites.yaml`. Login, proxy and browser state continue to use the existing unified configuration.
5. First verify with local HTML/API samples and an isolated database, then do online verification on a limited number of pages. A new site must also show its status and backfill progress on the actual site management page.

Pagination requests must keep the site's original sort and filter parameters, and these parameters must not be lost when replacing the page number. Forums should sort by newest creation time first; if the source only supports other sort orders, document the coverage limits caused by content moving during paging. Pinned topics and paging overlaps on the same page should be deduplicated by stable topic identifier.

`collect_paginated_seed(site_name, config, fetch_page, plan_details=adapter.plan_details)` pagination callback accepts `(source_url, page, collected_at)` and returns `(parsed_section, raw_page, has_more, id_signature, page_url)`. `plan_details` reuses the adapter's existing version and evidence deduplication rules to decide whether the newest page still has content that actually needs processing. `parsed_section` must contain at least `section` and `topics`, and topics contain `full_url`; `source_count` records the count before filtering, so a fully filtered page is not mistaken for the last page. The returned `SeedResult.metadata.cursor_updates` are written by the execution entry point after the candidates are stored; adapters must not save cursors early.

MyBB Forums fully parse the topics returned by each request and control discovery volume by the number of pages requested, preventing topics at the end of a page from being permanently missed after `max_topics_per_run` truncation. Changan continues to use this field as the per-page size for API requests; if the server returns a smaller page size, paging continues based on the actual response and total.

Each candidate's `DetailTask.metadata` contains `source_version`, `section` and `discovery_lane` (`recent` or `backfill`), plus the topic ID, mirror file name and anything else the site needs. Detail `persist` must accept an optional `connection`; when the caller provides a connection, it must not commit or close it itself, because the execution entry point puts the lease check, detail write and version completion in the same transaction. `frontier_artifact_only` tasks use `restore_detail_artifacts` to reuse saved JSON/HTML whose hash matches the database body to supplement screenshots, without re-requesting the body. Screenshots still follow the existing browser queue and concurrency limits.

Cursors may only advance after the page has been parsed successfully and the candidates persisted. Login pages, CAPTCHA pages, request failures and abnormal empty responses must not be treated as the last page. The last page is confirmed from trustworthy pagination metadata; duplicate page signatures prevent infinite scanning when a source ignores the page number. A failure in one section should keep its cursor so other sections can continue.

Error page detection must distinguish the main page from auxiliary UI. Normal lists, explicitly empty lists and body text may include a header login link, sidebars, pop-ups or quoted text; these alone cannot serve as evidence of a login, CAPTCHA or missing post. Hidden topic links, navigation links and hints inside login forms also cannot prove a list is valid. Main login templates, main-document challenges and explicit permission or missing-content errors must still be rejected.

Pagination and fallback fetch paths all preserve `kind`, `scope` and `retry_after` of `CollectionFailure`, and when all fail they provide a bounded per-path summary instead of just raising an aggregate exception with no reason. Rate limits of the same kind use the longest wait time; exhausted retry budgets, explicit unavailability, rate limiting and restricted results continue to follow the existing early-termination rules.

These attributes are preserved when exceptions pass through queue retries. Failure records of seed tasks carry a reason-type prefix so the existing management page can classify them by actual reason; retry waits are never shorter than the source requires. Task records and retry exceptions use redacted, safe summaries.

When some pages succeed, `SeedResult.metadata.pagination_errors` and `payload.pagination_errors` both record the failed page's source, page number, stage, exception type, reason, scope, retry wait and summary; the existing `latest.json` and task logs therefore keep traceable reasons, and cursor semantics for successful and failed pages are unchanged. Source URLs in diagnostics have credentials, query strings and fragments removed, and summaries are redacted and length-limited; never write cookies, authentication headers, keys or raw error HTML.

## Versions, completion and recovery

The discovered version `observed_version` is the most recently observed content version, and the success version `fetched_version` is the version already stored. A claimed task must be bound to the version at the time; if a new version is found during fetching, completing the old task can only confirm the old version, and the new version stays in the pending queue. These states are managed by `observe_frontier`, `claim_frontier` and `complete_frontier` in [crawl_frontier.py](./src/darkweb_collector/crawl_frontier.py).

The content hash should cover stable fields that affect intelligence analysis, such as the title, body summary, attachment identifiers and meaningful update times. Display counters such as view counts and likes do not trigger a body refetch; whether fields such as price and category affect the version is up to the site's intelligence needs. View count changes in the Changan list should not exhaust the detail quota.

A version is confirmed complete only after the detail has been persisted successfully. Repeated completion notifications must be idempotent, and late old tasks must not overwrite the state of new tasks. Dispatch reservations last 60 seconds; after a successful publish the task enters `queued`, and queued tasks are not re-dispatched because a running lease expired. A task enters `running` and starts its running lease only after obtaining an execution slot. An expired running lease is not evidence that a live process has exited: supervised tasks must first confirm that their entire process tree has exited before reclaiming the task, the pending record and the site execution slot. Expired queue records no longer occupy the dispatch window, and late old messages only end their own unfinished records. A dispatch failure only releases reservations that still belong to that dispatch and cannot overwrite a fast worker that has already started or completed. While browser evidence is incomplete, the completion state must be kept, and having obtained the body must not be mistaken for all evidence being complete.

Old-format published backlog is first marked `legacy_queued`; on first delivery it is returned to database `pending` and the old delivery record ended within the same transaction, and then the original message is acknowledged. Version and evidence progress are kept and old tokens become invalid; historical tasks are then dispatched at low priority by the new window, without cyclic ETA retry deliveries. If the transaction fails, the original message is requeued. Existing items under migration still count toward `inflight`, and the new dispatch window is bounded separately by the concurrency limit.

Prefer HTTP/API paths that can reliably obtain valid body text. Only requests that actually need page rendering or supplementary browser evidence consume browser resources. Once body and screenshot can run independently, screenshots must be bound to a content version; a stored body version must not be updated repeatedly just because a screenshot is missing.

## Site-wide failure handling and retry budgets

`source_closed` means the main page explicitly announces the site is down, backing off for at least 1 hour; `source_moved` means the main entry announces a migration, backing off for at least 6 hours. Browser verification such as DNSProxy is classified as `blocked`, not as an empty body or no posts. Migration announcements are only pending-verification leads and do not change the site address automatically. HTTP error status is kept together with the page reason, and normal posts, quotes, page headers and hidden login UI must not trigger these site-level decisions.

Details from all sources are first persisted to the SQL pending table and then published according to each site's actual capacity. Busy resources and back-off do not trigger an immediate re-dispatch chain; scheduled dispatch keeps advancing waiting tasks. When parse errors of the same type appear for several different targets within 15 minutes, details are paused separately with progressively longer waits; newest-list discovery keeps running, and historical backfill waits for capacity to recover.

Windows Startup and scheduling check the activity logs of managed old versions referenced by the database. They are taken over only when the supervisor process, the worker's PID and creation time, the Windows Job process tree and the database task identity can all be confirmed; logs of live processes, mismatched identities, corrupted logs or logs that cannot be verified are kept. The stop flow first confirms process exit and completes task recovery, then performs Garnet's final persistence, and existing intelligence is never deleted by recovery.

All registered adapters manage persistent retry budgets and execution ownership through the shared detail entry point, including sources that do not use the paginated pending-fetch mechanism. Adapters use `CollectionFailure` to provide explicit reasons; ordinary empty responses, unknown pages, HTTP 404/410 and parse failures must not be treated directly as a deleted post. `NoGoods`/4007 is interpreted only by the Changan adapter; forum deletion detection must match the site's explicit error template. Login, CAPTCHA and permission prompts must not be treated as valid body text, and normal articles whose body quotes these prompts must not be misjudged either.

| Reason | Default handling |
| --- | --- |
| Explicitly unavailable, single-post permission restriction | Target cools down for 24 hours, then is rechecked at low frequency; original body and evidence are kept |
| Login expired, rate limited | The site cools down for at least 30 minutes; insufficient permission on a single post does not pause other posts |
| Browser verification | Lists cool down for at least 15 minutes, details for at least 30 minutes |
| Source shut down, entry migrated | Cool down for at least 1 hour and 6 hours respectively; migration addresses need separate verification |
| Network or timeout | The first two failures wait 60 and 300 seconds respectively; after three consecutive failures, wait 1 hour |
| Empty body, parse failure or unknown result | First wait 15 minutes, then 1 hour on another failure; existing body text is not cleared |
| Valid body but missing screenshot | The body is committed first and marked `partial`; after 1 hour only the screenshot is backfilled |

During failure recovery, main-document requests for each site/target address share a persistent budget of 6 per hour, which resets to zero after a successful store. HTTP, proxy and browser fallback paths all count toward it, and adapters must not stack independent repeat loops to get around the budget. Recovery rounds can still use bounded fallback paths; what persistent failure limits is the round frequency, so it never keeps trying only the first path. Changes to fields such as observation time or view count must not reset the failed-request budget; a real source version change can trigger an earlier recheck but is still bound by the budget. A manual forced run clears the cooldown and budget of targets not currently executing, without preempting live tasks.

Records in cooldown stay in the pending list but are not treated as currently executable new tasks and do not take up the executable capacity for historical discovery. When executable new items exist they are processed first; when there are none, historical discovery is still limited by the small window and configured page count. During site-level detail back-off the newest list is still checked, and historical backfill pauses while keeping its cursor.

Windows The launcher uses supervised `solo` consumer processes. The total detail time limit defaults to 300 seconds for public sites and 600 seconds for Onion sites; `detail_task_timeout_seconds` can be set to 60–900 seconds. The TTL of site execution slots covers at least the total time limit plus a 90-second cleanup margin, and a database site admission lock prevents overlapping execution after the message service lease expires. The daemon checks every 15 seconds, and a Windows Job Object contains browser descendant processes; tasks are recovered only after all of them are confirmed to have exited. When cleanup or database/message service recovery fails, logs are kept and replacement processes are blocked.

When the console confirms there is no queue consumer, it returns `worker_unavailable` and does not start threads or process pools that bypass the daemon. Explicit one-off CLI calls still use transport timeouts and the persistent request budget, but do not have the forced-exit guarantee of the queue daemon.

Database initialization automatically adds `crawl_detail_control`, `crawl_site_control`, `crawl_detail_results` and the necessary indexes, without deleting historical data. Persisting valid body text, task completion and pending version confirmation use the same transaction; tasks with empty results or no actual body written must not be recorded as successful. `detail_yield_24h` of `/api/jobs` separately provides the number of new, updated and unchanged raw body records, plus the number of tasks with pending evidence; these numbers do not equal the number of new normalized intelligence records and do not retroactively rewrite task history from before the upgrade.

## Collection overview and statistics definitions

`/collector-control/overview` Provides three views: output, throughput and backlog; site summaries and real task history from `/collector-control/tasks` are paginated on the server. Site-wide metrics do not change with the current table's pagination or search. Last success and failure are read independently per site, so skipped tasks do not crowd out other sites' status. Enabled but idle sites show the waiting reason, and disabled sites are marked separately.

New body text comes from detail persistence results; newly visible intelligence is registered in the normalization publish transaction, and updates to existing events, replacement of deduplicated master records and full rebuilds are not double-counted. On upgrade only a baseline is registered for existing intelligence, and old data is not counted as new. Backlog is sampled by the scheduler every minute and kept for 8 days, counted separately for new posts and historical backfill; items whose body has been obtained and only need evidence do not count as pending new posts. Periods with no historical records are left blank, the page indicates where statistics coverage starts, and GET endpoints never trigger collection or fabricate historical snapshots.

The overview supports the last 1 hour, 24 hours and 7 days, using bounded aggregation and a short cache. Partially completed details clear stale body parse errors and show that evidence is pending. When statistics are first enabled, a source is down, an entry migration is pending verification or manual verification is needed, judge by the page hints; output cannot be measured solely by the number of tasks currently running at the same time.

## Verification and efficiency evaluation

Onboarding must verify at least: network requests actually happen from the first page to later pages; cursors continue after a restart; pinned topics and cross-page overlaps are not stored twice; other sections still advance after one section fails; remaining candidates are not lost when detail quota is insufficient; later tasks can still be claimed while earlier tasks are in cooldown; dispatch failures, lease expiries and duplicate completions all recover; version changes during fetching are not confirmed by old tasks; the newest page is still checked when the backlog reaches the threshold.

Performance should record, per hour, the number of valid new or substantively updated items after deduplication, the delay from discovery to searchability, queue wait time, request success rate and evidence completeness. List scan counts, task execution counts and database update counts cannot substitute for valid intelligence output.

Increasing the historical page budget speeds up coverage of old data but also increases source requests and detail backlog; increasing the newest page budget suits sections that update faster than the polling interval. Tune budgets with runtime data first, then tune workers and egress capacity. This mechanism provides a sustainable default strategy and cannot guarantee absolute maximum efficiency on every site. Sources that support incremental APIs, sitemaps, time cursors or only a few announcements should prefer their more suitable discovery interfaces and reuse the same version and recovery semantics.
